The shielded components show private balances, scan progress and proofs. They don't know which privacy protocol is behind them. They talk to a **shielded engine**: a small interface that wraps one protocol SDK and reports its state in neutral terms.

<Aside type="caution" title="Preview">
  Two engines exist. The [mock engine](/components/mock-shielded-engine/) imitates the Railgun SDK's behaviour without a network or real funds. The [Privacy Pools engine](/components/privacy-pools-engine/) shields into and unshields from the real Privacy Pools contracts. The interface will grow as the unshield and private send components are built.
</Aside>

Everything below runs on the mock. Unlock it, then use the buttons to make things happen.

## Usage

Create an engine once and put it in context. Shielded components go inside. They don't need a wagmi provider themselves; you will have one anyway for the public side.

```tsx
import { ShieldedProvider } from "@/components/shielded-provider";
import { createMockShieldedEngine } from "@/lib/mock-shielded-engine";

const engine = createMockShieldedEngine();

<Web3Provider>
  <ShieldedProvider engine={engine}>
    <App />
  </ShieldedProvider>
</Web3Provider>;
```

## Hooks

```tsx
import {
  useShieldedAccount,
  useShieldedEngine,
  useShieldedState,
} from "@/components/shielded-provider";

// The engine itself, to call its methods.
const engine = useShieldedEngine();

// Whether a private account exists and is unlocked, and its private address.
const { status, address } = useShieldedAccount();

// Any piece of engine state, re-read when an event fires.
const syncing = useShieldedState("sync", (e) => e.getSync(1).status === "syncing", false);
```

`useShieldedState` takes the event to listen to, a function that reads from the engine, and the value to use on the server. Private state never reaches server HTML.

## The interface

```ts
interface ShieldedEngine {
  id: string;
  shieldsNative?: boolean;

  account: {
    status(): "none" | "locked" | "unlocked";
    create(password: string): Promise<{ mnemonic: string }>;
    import(mnemonic: string, password: string): Promise<void>;
    unlock(password: string): Promise<void>;
    lock(): void;
    address(): string | null;
  };

  subscribe(event: "account" | "sync" | "balances", listener: () => void): () => void;

  getSync(chainId: number): ShieldedSync;
  getBalances(chainId: number): readonly ShieldedTokenBalance[] | undefined;
  getTransaction(chainId: number, hash: Hash): ShieldedTransaction | undefined;

  sync(chainId: number): Promise<void>;
  retryProofs(chainId: number): Promise<void>;

  quoteShield(draft: ShieldDraft): Promise<ShieldQuote>;
  prepareShield(
    draft: ShieldDraft,
    options: { sign(message: string): Promise<Hex> }
  ): Promise<PreparedShield>;

  prove(
    draft: PrivateDraft,
    options: { onStage(stage: ProofStage): void; signal?: AbortSignal }
  ): Promise<ProvedOperation>;
  quote(draft: PrivateDraft): Promise<PrivateQuote>;
  submit(operation: ProvedOperation): Promise<{ hash: Hash }>;
}
```

Three rules make it easy to build UI on:

- **Listeners get no payload.** An event says "this changed". The new state comes from the getters, so a component can never hold an event that disagrees with them.
- **Getters return the same reference until the state changes.** That is what lets the hooks use `useSyncExternalStore`.
- **Balances are one snapshot per chain.** Protocol SDKs report balances in pieces. The engine merges them, so the states of a token always add up.

### Balance states

A private balance is split by what can be done with it. Each engine maps its protocol's own states onto these five, and protocol names stay inside the engine.

| State | Meaning |
| --- | --- |
| `spendable` | Ready to spend. |
| `pending` | Recently shielded, waiting out the protocol's standby period. |
| `proving` | Proofs for these funds are submitted and being checked. |
| `incomplete` | A proof is missing. `retryProofs` tries again. |
| `restricted` | Can't be spent privately. Can only return to the address it came from. |

### Sync

```ts
type ShieldedSync = {
  stage: "notes" | "transactions";
  status: "idle" | "syncing" | "synced" | "error";
  progress: number; // 0 to 1 within the stage
  error?: string;
};
```

`progress` is what the protocol reports, and it is not monotonic: it restarts for each stage, can jump backwards inside one, and may be 0 when the scan is done. [Shielded Sync Status](/components/shielded-sync-status/) turns it into a bar that only moves forward.

`sync(chainId)` resolves when the scan settles. A failed scan is reported through `getSync`, not by rejecting.

### Shielding

```ts
type ShieldDraft = { chainId: number; token: Address; amount: bigint };
type ShieldQuote = {
  fee: bigint;
  received: bigint;
  standby: number; // seconds
  spender?: Address; // contract to approve before the shield is sent
  needsSignature: boolean; // prepareShield will ask the wallet to sign
};
type PreparedShield = { transaction: { to; data?; value? } };
```

- `quoteShield` signs and sends nothing. It lets the UI show the cost first, and lay out every wallet step before the first one: `spender` says whether an approval is needed, `needsSignature` whether a signature is.
- `prepareShield` builds the transaction. The public wallet sends it; the engine never does. Some protocols derive a one-off key from a wallet signature: the engine then calls `sign(message)`, at most once, and a rejected signature rejects the promise with the wallet's error.
- `shieldsNative` says the protocol takes native currency as it is. A draft then carries the native token's address and the transaction carries the amount as its `value`. Without it, native currency is held as its wrapped token.
- `account.address()` may stay `null` on a protocol that has no private address, like Privacy Pools v1.
- `getTransaction(chainId, hash)` is how the UI knows a shield really arrived. It returns nothing until a scan has found the funds, then `{ kind: "shield", token, amount, state }`. A mined receipt alone is not proof.

See the [Shield](/blocks/shield/) block and [Shielded Transaction Status](/components/shielded-transaction-status/).

### Proofs

`prove` reports stages (`loading-circuits`, `proving`, `verifying`), not a percentage: provers don't report a real one. See [Proof Progress](/components/proof-progress/).

### Private operations

An unshield moves tokens from the private balance to a public address. It takes three calls:

```ts
const draft = { kind: "unshield", chainId: 1, token, amount, recipient } as const;

const { fee, received } = await engine.quote(draft);
const operation = await engine.prove(draft, { onStage });
const { hash } = await engine.submit(operation);
```

- `quote` says what the operation costs now. It proves nothing. It rejects when the draft can't be done, with a message fit to show.
- `prove` returns a `ProvedOperation`: the draft, the fee the proof commits to in `quote`, and `expiresAt`. The fee can differ from an earlier `quote`, so show the operation's own.
- `submit` sends it. The engine does this itself, through the protocol's relayer where there is one, so the public wallet is not involved. It resolves when the transaction is broadcast, not mined. A proof can be submitted once.

After `submit`, call `sync` once the transaction is mined, as after a shield.

## Not in the interface yet

These are planned and arrive with the components that need them: private transfers, a choice of relayer, and capability flags per engine.

## Writing an engine

An engine is any object that implements `ShieldedEngine`. Keep the protocol SDK, its event shapes and its vocabulary inside it:

- Merge the SDK's balance events into one snapshot before you notify listeners.
- Map the SDK's balance buckets onto the five states.
- Scan after `unlock`, and again on an interval, since most SDKs don't push balance changes.
- Honor the `AbortSignal` in `prove` and reject with its reason.
- In `prepareShield`, refuse to return a transaction an ordinary wallet can't send as a plain call (an EIP-7702 transaction, for one). Throw instead of dropping fields.
